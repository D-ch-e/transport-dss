# XAI DSS — 五週小組分工計畫

> 專題：可解釋交通決策支援系統  
> 組員人數：3 人  
> 預計時長：5 週  
> 分工方式：依模組與系統層級分工，避免只以簡報或報告分工。

---

## 一、角色總覽

### 成員 A：資料與後端負責人

**主要負責模組**：

- M1 API Client / 資料整合
- M2 Input Validator / 輸入驗證
- M7 Static Data / 靜態資料

**核心責任**：

- 整理交通基礎資料
- 建立靜態資料表
- 設計資料輸出格式
- 處理輸入驗證與錯誤訊息
- 提供穩定資料給模型端使用

---

### 成員 B：模型與 XAI 負責人

**主要負責模組**：

- M3 Feature Engineer / 特徵工程
- M4 Decision Model / 決策模型
- M5 XAI Report / 可解釋層

**核心責任**：

- 設計成本、時間、便利性三大特徵
- 建立加權評分模型
- 建立決策樹模型
- 產生推薦原因與可解釋輸出
- 驗證模型結果是否合理

---

### 成員 C：UI、整合與測試負責人

**主要負責模組**：

- M6 Streamlit UI / 使用者介面
- M8 Tests / 整合測試
- README / Demo / 專案整合

**核心責任**：

- 建立 Streamlit 操作介面
- 串接資料模組與模型模組
- 顯示推薦結果、比較表與 XAI 解釋
- 整理 README 與 Demo 流程
- 負責最終系統整合與展示

---

## 二、Week 1 — 專案骨架與最小可行系統

### Week 1 共同目標

建立專案基本架構，完成一個可以從輸入到輸出跑通的最小可行系統（MVP）。本週不追求模型完整度與 UI 美觀，重點是讓三個人的工作能開始串接。

---

### Week 1 成員 A：資料與後端

#### Week 1 成員 A 本週任務

- 建立 `data/static/` 資料夾。
- 建立初版 `fare_table.csv`。
- 建立初版 `city_hub_map.json`。
- 定義支援的起訖地城市，例如台北、台中、台南、高雄。
- 整理四種交通方式的初步資料：
  - 高鐵
  - 台鐵
  - 客運
  - 租車
- 設計資料輸出格式，讓模型端可以直接使用。
- 撰寫初版 `data/input_validator.py`。

#### Week 1 成員 A 本週交付物

- `data/static/fare_table.csv`
- `data/static/city_hub_map.json`
- `data/input_validator.py` 初版
- 資料欄位說明文件或簡短註解

#### Week 1 成員 A 完成標準

- 至少支援 3 組城市路線。
- 每條路線至少包含四種交通方式的成本與時間估計。
- 能檢查基本輸入是否有效。

---

### Week 1 成員 B：模型與 XAI

#### Week 1 成員 B 本週任務

- 定義三大特徵：
  - cost
  - time
  - convenience
- 設計成本、時間、便利性的基本計算方式。
- 建立 `features/feature_engineer.py` 初版。
- 建立 `models/scoring_model.py` 初版。
- 先使用簡單加權公式產生推薦結果。
- 與成員 A 確認資料輸入格式。

#### Week 1 成員 B 本週交付物

- `features/feature_engineer.py` 初版
- `models/scoring_model.py` 初版
- 初版特徵計算邏輯說明

#### Week 1 成員 B 完成標準

- 輸入交通方式資料後，可以輸出每種交通方式的三大特徵。
- 可以根據預設權重產生交通方式排序。

---

### Week 1 成員 C：UI、整合與測試

#### Week 1 成員 C 本週任務

- 建立專案基本資料夾結構。
- 建立 `ui/app.py` 初版。
- 建立 Streamlit 側邊欄輸入介面。
- 先用假資料或成員 B 的初版模型顯示推薦結果。
- 建立 GitHub repo 或共同協作資料夾。
- 建立 `requirements.txt` 初版。
- 建立 README 初版架構。

#### Week 1 成員 C 本週交付物

- `ui/app.py` 初版
- `requirements.txt` 初版
- `README.md` 初版
- 專案資料夾結構

#### Week 1 成員 C 完成標準

- 可以執行 Streamlit。
- UI 可以輸入基本條件。
- 頁面能顯示一個初步推薦結果。

---

### Week 1 檢查點

- [ ] 專案資料夾結構已建立。
- [ ] 靜態資料可以被讀取。
- [ ] 特徵與評分模型可以初步運作。
- [ ] Streamlit 可以開啟並顯示基本結果。
- [ ] 三位成員確認資料格式一致。

## 三、Week 2 — 特徵工程與評分模型穩定化

### Week 2 共同目標

完成交通方式比較的核心邏輯，讓系統可以根據使用者偏好權重改變推薦結果。

---

### Week 2 成員 A：資料與後端

#### Week 2 成員 A 本週任務

- 補齊更多靜態資料路線。
- 檢查 `fare_table.csv` 欄位是否符合模型需求。
- 補上租車成本參數，例如：
  - 基本租車費
  - 油耗或油資估算
  - 停車或彈性成本估算
- 強化 `input_validator.py`：
  - 人數範圍
  - 預算下限
  - 行李量合理性
  - 起訖地是否相同
- 統一錯誤訊息格式，方便 UI 顯示。

#### Week 2 成員 A 本週交付物

- 更新版 `fare_table.csv`
- 更新版 `city_hub_map.json`
- 完整版 `input_validator.py`
- 資料來源與資料假設說明

#### Week 2 成員 A 完成標準

- 靜態資料足以支援主要 Demo 情境。
- 無效輸入能回傳清楚的中文錯誤訊息。

---

### Week 2 成員 B：模型與 XAI

#### Week 2 成員 B 本週任務

- 完成 Min-Max 正規化邏輯。
- 明確定義 cost、time、convenience 的分數方向。
- 處理成本與時間分數：數值越低是否代表越好。
- 完成加權評分模型。
- 加入使用者權重：
  - 成本權重
  - 時間權重
  - 便利性權重
- 設計 10 組測試情境。

#### Week 2 成員 B 本週交付物

- 完整版 `feature_engineer.py`
- 完整版 `scoring_model.py`
- 10 組模型測試案例
- 特徵與權重設計說明

#### Week 2 成員 B 完成標準

- 權重改變時，推薦結果能合理變化。
- 能輸出四種交通方式的完整排序。

---

### Week 2 成員 C：UI、整合與測試

#### Week 2 成員 C 本週任務

- 在 Streamlit UI 加入三個權重滑桿。
- 顯示權重歸一化後的比例。
- 串接成員 A 的輸入驗證模組。
- 串接成員 B 的特徵工程與評分模型。
- 顯示多方案比較表。
- 加入最高分方案標示。

#### Week 2 成員 C 本週交付物

- 更新版 `ui/app.py`
- 多方案比較表 UI
- 權重滑桿 UI
- 初版整合測試紀錄

#### Week 2 成員 C 完成標準

- 使用者調整權重後，推薦結果會重新計算。
- UI 能顯示每種交通方式的成本、時間、便利性與總分。

---

### Week 2 檢查點

- [ ] 靜態資料已補齊 Demo 所需路線。
- [ ] 權重調整會影響推薦結果。

## 四、Week 3 — 決策樹與 XAI 解釋

### Week 3 共同目標

讓系統符合「可解釋 AI 決策支援系統」的核心要求。不只給推薦，也要清楚說明推薦原因。

---

### Week 3 成員 A：資料與後端

#### Week 3 成員 A 本週任務

- 檢查資料是否足夠支援 XAI 情境。
- 若時間允許，開始實作 `data/api_client.py`。
- 設計 API fallback 機制。
- 補上資料來源與資料限制描述。
- 協助成員 B 處理模型所需資料格式。

#### Week 3 成員 A 本週交付物

- `data/api_client.py` 初版或 fallback 設計
- 資料限制說明
- 更新後的靜態資料

#### Week 3 成員 A 完成標準

- 即使不串接 API，系統仍可穩定使用靜態資料。
- 資料格式能支援模型與 XAI 輸出。

---

### Week 3 成員 B：模型與 XAI

#### Week 3 成員 B 本週任務

- 建立 `models/decision_tree.py`。
- 設計決策樹訓練資料或 rule-based synthetic data。
- 訓練初版決策樹模型。
- 從決策樹提取 decision path。
- 將 decision path 轉成繁體中文 IF–THEN 說明。
- 建立 `xai/xai_report.py`。
- 實作特徵貢獻分析。
- 實作反事實提示，例如：
  - 若預算降低，推薦可能改變
  - 若人數增加，租車可能更有利
  - 若時間權重提高，高鐵可能更有利

#### Week 3 成員 B 本週交付物

- `models/decision_tree.py`
- `xai/xai_report.py`
- 中文決策路徑輸出
- 反事實解釋輸出

#### Week 3 成員 B 完成標準

- 系統能提供推薦原因。
- 系統能顯示至少一段中文 IF–THEN 決策路徑。
- 系統能提供至少一則反事實提示。

---

### Week 3 成員 C：UI、整合與測試

#### Week 3 成員 C 本週任務

- 在 UI 加入 XAI 解釋區塊。
- 顯示：
  - 特徵貢獻
  - 決策路徑
  - 反事實提示
- 如果成員 B 提供數值貢獻，製作簡單長條圖。
- 加入模型不一致 warning 顯示。
- 設計情境模擬區塊。

#### Week 3 成員 C 本週交付物

- XAI 解釋 UI
- 特徵貢獻圖或表格
- 決策路徑文字區塊
- 反事實提示框

#### Week 3 成員 C 完成標準

- 使用者可以看到「為什麼推薦這個交通方式」。
- UI 能清楚區分推薦結果與解釋內容。

---

### Week 3 檢查點

- [ ] 決策樹模型可以產生結果。
- [ ] 系統可以輸出中文決策路徑。
- [ ] 系統可以輸出反事實提示。
- [ ] UI 已加入 XAI 區塊。
