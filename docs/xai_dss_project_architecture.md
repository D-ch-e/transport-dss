# XAI DSS — 可解釋交通決策支援系統

## 一、專題概述

**專題名稱**：XAI DSS — 可解釋交通決策支援系統  
**專題性質**：Python 資料分析與機器學習期末小組專題  
**組員人數**：3 人  
**預計開發時程**：約 5 週  
**核心主軸**：可解釋的 AI 決策支援系統（Explainable AI Decision Support System）

### 專題目標

本專題旨在設計一個以 Python 為核心的可解釋 AI 決策支援系統，協助使用者在多種交通方式（高鐵、台鐵、客運、租車）之間做出選擇。系統不僅提供推薦結果，也會說明「為什麼如此推薦」以及「在什麼條件改變時推薦結果可能不同」。

本系統的重點不是取代使用者做決策，而是透過資料分析、機器學習模型與可解釋方法，協助使用者理解成本、時間與便利性之間的取捨。

---

## 二、使用情境與決策問題

### 2.1 系統應用情境

本系統應用於日常通勤與短程旅遊規劃情境。使用者在規劃跨縣市移動時，常需要在多種交通方式之間選擇，例如：

- 高鐵
- 台鐵
- 客運
- 租車

在實際情境中，交通選擇不只取決於時間，也會受到人數、行李量、預算與個人偏好的影響。例如，多人同行時租車的平均成本可能下降；行李較多時，大眾運輸的便利性可能降低；若時間急迫，高鐵可能更具優勢。

### 2.2 使用者面臨的決策困難

使用者在交通選擇時通常需要同時考量多個彼此衝突的因素：

- 較快的交通方式通常成本較高
- 較便宜的交通方式可能耗時較長
- 行李較多可能降低大眾運輸便利性
- 多人同行會改變租車與大眾運輸的成本比較
- 不同使用者對成本、時間與便利性的重視程度不同

因此，單純依靠單一條件（例如最短時間或最低價格）並不足以支援完整決策。

### 2.3 本系統欲支援的具體決策

本系統支援的具體決策是：

> 在給定起訖地、人數、行李量、預算與時間偏好的條件下，協助使用者比較多種交通方式，並理解系統為何推薦某一方案。

系統會輸出：

1. 最佳交通方式建議
2. 各交通方式的分數與排序
3. 成本、時間與便利性的比較
4. 影響推薦結果的主要因素
5. 條件改變時可能造成推薦改變的反事實提示

## 三、系統整體架構

### 3.1 架構層次

```text
輸入層（User Input）
  ↓
資料層（Input Validator / Static Data / API Client）
  ↓
特徵工程層（Feature Engineering）
  ↓
決策模型層（Scoring Model + Decision Tree）
  ↓
可解釋層（XAI Report）
  ↓
展示層（Streamlit UI）
```

### 3.2 系統流程

1. 使用者輸入起點、終點、人數、行李量、預算與時間偏好。
2. 系統進行輸入驗證，確認資料格式與範圍合理。
3. 系統讀取靜態交通資料，或在可行時串接外部 API。
4. 特徵工程模組計算 cost、time、convenience 三類特徵。
5. 決策模型根據權重與模型規則計算各交通方式分數。
6. XAI 模組產生推薦原因、決策路徑與反事實解釋。
7. Streamlit UI 顯示推薦結果、多方案比較與可解釋分析。

## 四、模組劃分與職責

## M1 · API Client（資料整合模組）

**路徑**：`data/api_client.py`

### 功能

- 取得各交通方式的距離、時間與基礎成本資料
- 讀取靜態資料作為主要資料來源或 fallback
- 若時間允許，可串接 Google Maps API
- 統一輸出資料格式供後續模組使用

### 主要輸出

```python
{
    "mode": "高鐵",
    "cost": 1350,
    "duration_min": 110,
    "distance_km": 345,
    "source": "static"
}
```

---

## M2 · Input Validator（輸入驗證模組）

**路徑**：`data/input_validator.py`

### 功能

- 驗證人數是否在合理範圍內
- 驗證預算是否為有效數值
- 驗證行李量與人數組合是否合理
- 檢查起訖地是否存在於支援城市列表
- 回傳可供 UI 顯示的繁體中文錯誤訊息

### 輸出格式

```python
(valid: bool, message: str)
```

---

## M3 · Feature Engineer（特徵工程模組）

**路徑**：`features/feature_engineer.py`

### 功能

- 計算交通方式的成本特徵（cost）
- 計算交通方式的時間特徵（time）
- 計算交通方式的便利性特徵（convenience）
- 進行 Min-Max 正規化
- 將原始資料轉換成模型可比較的格式

### 三大特徵

| 特徵 | 說明 |
|---|---|
| cost | 總成本或人均成本，包含票價、租車成本等 |
| time | 預估總時間，包含移動、等待與轉乘時間 |
| convenience | 根據行李、人數、轉乘與彈性估算便利性 |

---

## M4 · Decision Model（決策模型模組）

**路徑**：

- `models/scoring_model.py`
- `models/decision_tree.py`

### 功能

- 使用加權評分模型產生各交通方式分數
- 使用決策樹模型產生可解釋的推薦規則
- 比較加權模型與決策樹模型是否一致
- 若兩模型推薦不同，回傳 warning 供 UI 顯示

### 評分概念

```text
score = w_cost × cost_score + w_time × time_score + w_convenience × convenience_score
```

其中權重由使用者偏好決定，並進行歸一化處理。

---

## M5 · XAI Report（可解釋層模組）

**路徑**：`xai/xai_report.py`

### 功能

- 產生特徵貢獻分析
- 將決策樹 decision path 轉換為中文 IF–THEN 說明
- 產生反事實解釋
- 統一封裝成 dict 給 UI 使用

### 輸出範例

```python
{
    "top_reason": "時間權重較高，因此高鐵獲得最高分",
    "decision_path": "若時間需求為急，且預算足夠，則推薦高鐵",
    "counterfactual": "若預算降低至 900 元以下，推薦可能改為客運"
}
```

## 七、設計決策與權衡

## Decision 1：可解釋性 vs. 預測準確度

本系統選擇加權評分模型與決策樹，原因是這兩種方法容易解釋，能讓使用者理解推薦結果背後的邏輯。雖然更複雜的模型可能在某些資料情境下提供更高準確度，但其黑箱性較高，不符合本專題「可解釋決策支援」的核心目標。

### 放棄的替代方案

- 深度學習模型
- 複雜集成模型
- 完全黑箱式推薦模型

### 限制

- 較難捕捉複雜非線性關係
- 模型表現依賴特徵設計品質

---

## Decision 2：靜態／模擬資料 vs. 即時資料

本系統優先使用靜態資料與情境設計資料，原因是期末專題時程有限，靜態資料較容易控制、測試與重現。即時交通資料雖然更貼近現實，但會增加 API 申請、連線穩定性、資料格式與錯誤處理的複雜度。

### 放棄的替代方案

- 完全依賴 Google Maps API
- 即時票價與即時班次查詢
- 即時路況整合

### 限制

- 無法反映即時交通狀況
- 實際票價與時間可能與系統資料不同

---

## Decision 3：建議式決策支援 vs. 自動決策

本系統定位為部分自動化的決策支援工具。系統會自動完成資料處理、模型計算與解釋產生，但不會替使用者做最終決策。使用者仍可依自身情境與偏好判斷是否採納系統建議。

### 放棄的替代方案

- 直接指定唯一最佳方案
- 自動替使用者完成訂票或租車
- 隱藏模型推論過程

### 限制

- 使用者仍需自行理解與判斷
- 若使用者誤解結果，仍可能做出不適合的選擇

## 八、AI 角色與系統自主性

### AI 在系統中的角色

本系統中的 AI 主要扮演以下角色：

- **建議**：推薦較適合的交通方式
- **分析**：比較各交通方式在成本、時間與便利性上的差異
- **模擬**：讓使用者調整條件後觀察推薦變化
- **解釋**：說明影響推薦結果的主要因素

### 系統自動化程度

本系統屬於「部分自動化」的決策支援系統。系統會自動完成資料整合、評分計算、模型判斷與解釋產生，但不會直接替使用者做出最終決策。

### 使用者如何介入與覆核

使用者可以透過以下方式介入：

- 調整成本、時間與便利性的權重
- 修改人數、行李量、預算與時間偏好
- 比較不同交通方式的原始數值
- 閱讀 XAI 解釋後自行判斷是否接受建議

## 九、系統邊界

## 系統會做什麼

- 比較多種交通方式
- 根據使用者條件產生推薦
- 顯示成本、時間與便利性的差異
- 提供推薦原因說明
- 支援情境模擬
- 提供決策輔助資訊

## 系統不做什麼

- 不保證現實中絕對最佳方案
- 不處理所有即時路況與突發狀況
- 不自動完成訂票或租車
- 不收集敏感個人資料
- 不將 AI 輸出視為最終決策

## 十、評估方法

本系統將透過以下方法進行評估：

### 10.1 一致性檢驗

確認模型輸出是否符合基本常識，例如：

- 人數增加時，租車的人均成本優勢應上升
- 時間權重提高時，高鐵應更容易被推薦
- 預算降低時，客運或台鐵應更容易被推薦

### 10.2 敏感度分析

調整成本、時間與便利性權重，觀察推薦結果是否合理變化。

### 10.3 極端情境測試

測試以下情境：

- 低預算
- 多人同行
- 行李量高
- 高度時間急迫
- 預算充足但便利性需求高

### 10.4 失敗案例分析

分析模型結果不合理或兩模型推薦不同的案例，並在系統中顯示 warning，提醒使用者此結果需要進一步判斷。
